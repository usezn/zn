### Security
- On Windows, `ZN_HOOK_DIR` was only checked to be a real folder, although the hook launcher kept there runs on every tool call. zn-gate now applies the same rule as on Linux and macOS: it refuses a folder when a link or junction is anywhere in its path, when its owner is not you, SYSTEM, Administrators or TrustedInstaller, or when its access list (or that of any folder above it, up to the drive root) lets other users delete it, replace it or change its permissions (and, for the folder itself, create files in it). A new folder is created private to your account, and the path is checked again after the launcher is written, this time with the launcher file itself (its owner and access list). zn-gate reads the access lists with the system PowerShell from System32 and a minimal environment (never a `powershell.exe` or `icacls.exe` found in the current folder or on PATH), refuses any reparse point (link, junction or synced folder) in the path, requires a new folder to be empty once it is private to your account, and writes launcher temp files with an unpredictable name that must not already exist. Every PowerShell that zn starts on Windows now gets a PSModulePath that names only the system module folder, and the access-list scripts use no cmdlet at all, only .NET types and operators (the answer is written line by line, with no `ConvertTo-Json`): Windows PowerShell otherwise looks in the user's own `Documents\WindowsPowerShell\Modules` first, where a module planted by the same account could replace a cmdlet and make the check report a forged answer. The hook scripts that zn writes for Cursor, Gemini CLI, Codex and Antigravity find `zn` and Node.js with .NET calls instead of `Get-Command` and `Test-Path`, and the confirmation dialog uses no cmdlet either.
