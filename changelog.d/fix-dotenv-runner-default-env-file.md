### Security
- The shell hook refuses `dotenvx run`, `dotenvx get` and the other `dotenvx` steps that load the default file, and `dotenv` (dotenv-cli) run without `-e`, when the project `.env` holds a plain-text secret or an encrypted value, the same as when the command names `.env` with `-f` (dotenvx) or `-e` (dotenv-cli). dotenv-cli has no `-f` or `--env-file` option and ignores them, so for it only `-e` counts as giving a file; `dotenv -f x -- printenv` still loads and is checked as `.env`. Before, only the form that typed the file name was checked, so `dotenvx run -- printenv` printed the values. With `--convention` (dotenvx) or `-c` / `--cascade` (dotenv-cli) the hook also checks every `.env.<name>` file in the folder, for example `.env.staging` and `.env.staging.local`, whichever environment name the command or `NODE_ENV` gives; the `.example`, `.sample` and `.template` files are left out. `dotenvx keypair` and `dotenvx ext` also check `.env.keys`. Only `dotenvx help`, `ls`, `gitignore`, and `--help` or `--version` before a step, are treated as loading nothing; any other `dotenvx` step, or one the hook cannot identify, is checked. The runner is found behind `env`, `sudo`, `command`, `nice`, `nohup`, `time`, `timeout` and the other wrappers the hook already reads. The check follows a `cd` or `pushd` earlier in the command and refuses one it cannot follow, it ignores file options that belong to the wrapped command instead of the runner, and, for every `dotenvx` step (also after an option placed before the step), it treats every word after `-f` / `--env-file` up to the next option or `--` as a file, since dotenvx takes several values (`dotenvx run -f other.txt .env` loads both): `run` judges each as a read, and `get`, `set`, `encrypt`, `decrypt` and the other steps refuse one that names a dotenv file. Each repeated `dotenv -e` is checked too. A project whose `.env` has no secret, or has none, is not affected.
