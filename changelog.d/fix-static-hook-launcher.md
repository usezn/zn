### Security
- On Linux, a user install for Claude Code and ZCode now starts the hook through a small
  statically linked launcher. `LD_TRACE_LOADED_OBJECTS` or `LD_DEBUG=help` in the agent's environment made the dynamic loader
  exit before the hook ran, so the call went ahead unchecked. The launcher runs before any loader and denies the call in the
  agent's own format when the environment has `LD_TRACE_LOADED_OBJECTS` set to any value (the empty string and `0` included), or any of `LD_PRELOAD`, `LD_AUDIT`, `LD_PROFILE`, `LD_LIBMAP`, `LD_32_PRELOAD`, `LD_TRACE_LOADED_OBJECTS_FMT1`, `LD_TRACE_LOADED_OBJECTS_FMT2`, `LD_TRACE_LOADED_OBJECTS_ALL`, `LD_DEBUG` (any value, not only `help`), `LD_DEBUG_OUTPUT`, `LD_PRELOAD_FDS`, `LD_LIBMAP_DISABLE`, `LD_LOADFLTR`, `DYLD_INSERT_LIBRARIES`, `DYLD_IMAGE_SUFFIX`, `DYLD_SHARED_CACHE_DIR` or `DYLD_SHARED_REGION` set to a value that is not empty, in exactly that upper case (the loader reads no other case). It removes every other loader variable
  (`LD_LIBRARY_PATH`, `LD_SHOW_AUXV` and the like) before it starts the hook. Without a matching launcher for the machine, or when the installed copy does not answer its test run as expected, the install keeps the earlier hook and says so. Codex CLI, Gemini CLI
  and GitHub Copilot CLI are detection only, and so is Antigravity until its launch form is run with the real agent (the Claude Code form was verified with a real Claude Code 2.1.331 on x86_64 Linux): `zn audit` reports the variables as critical, the hook cannot refuse them, the call goes ahead. Cursor (not verified) and project installs are not covered either
  (see the threat model).
