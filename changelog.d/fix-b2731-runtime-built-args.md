### Security
- The hooks now check file names that a command builds when it runs, not only the ones it spells out, in every command of the Node package. What the command itself fixes is worked out and checked like a typed name (a `.env` with values, a private key, a credential file, zn's own folder): a variable set earlier in the same command, a `for` loop over a fixed list, an array, `${name/x/y}` and the other `${...}` forms, `$(echo ...)` and `$(printf ...)` with known text, `read` and `xargs` fed by known text or by a list file, and `eval` or `sh -c` with known text. Each resolved reading of a command is also checked as a command line of its own, so the rules for specific programs read the resolved words too. What it does not fix is blocked when a protected file could be behind it: a name that is partly unknown and could be a protected one (`.e$x`, `$dir/.env`, `~/.aws/$f`), a name that is entirely unknown given to a program that shows, copies or sends its files (`cat`, `sed`, `cp`, `tar`, `scp`, `source`, ...), and `eval`, `sh -c`, `trap` or `source <(...)` with code zn cannot read, apart from the exact calls of a few well-known environment tools (`eval "$(ssh-agent -s)"`, `direnv hook <shell>`, `starship init <shell>`, ...). Output that can carry a name the command picked (`date` with a free format, `expr`, `openssl`, `stat`, `git config`, `git branch`) is no longer trusted, a git file list is looked up in the repository, an alias definition next to alias expansion is blocked, and a command nested deeper than zn follows is blocked. A list from `find`, `ls`, `grep -l` or a file on the disk is looked up and blocked only when it holds a protected file, and everyday commands such as `git commit -m "$(...)"`, `for f in src/*.ts`, `find ... | xargs grep` and `docker run -v "$(pwd)":/app` are not affected. A program whose own name is built at run time is still not checked. The Python package has no shell policy for protected paths, so none of this changes there.
