### Security
- Masking now runs inside the vault daemon. The scrubber asks it where the vault's values occur in a text and gets positions and secret names back; no call hands out the values (the `exactValues` request is gone), so a program that can talk to the daemon can no longer read every stored secret, including proxy-mode secrets and the `zn-gate connect` key, in one request.
- Every request for a value now names a destination (the hooks) or a purpose (`zn run`, `secrets_http_request`, `secrets_render_file`), and the daemon checks it against what it holds: the restoration table, the secret's mode, the commands, executables, hosts and places you allowed, and the organization policy. A request with no context, or one the daemon does not know, is refused and written to the audit log. The daemon never hands a value out for the assistant's own text. These names are declared by the caller: the checks and the record are new, but the daemon still does not prove which program is asking (see the threat model).
- `zn secret adopt`, `zn secret import` and `zn env shadow` no longer read a value back, `zn env unshadow` waits for your confirmation on the vault's own prompt before the plain text leaves the vault, and value comparisons are recorded and limited.
- On Linux and macOS the daemon refuses to start unless its socket, session key and folder belong to your user and are closed to others. A vault started by an older zn-gate counts as outdated: `zn unlock` restarts it.
