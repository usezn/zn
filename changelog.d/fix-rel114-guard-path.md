### Security
- The project hook and the fallback of the hook launcher now start `zn` and Node.js only from absolute PATH entries. Before, when the PATH held a relative or empty entry, a `zn` or `node` placed in the repository could run instead (the project hook on macOS and on Linux systems where `sh` is bash), and on Windows `zn.cmd` could start a `node.exe` or `node.bat` from the current folder. If you installed a 1.14.0 release candidate, run `zn hooks install` again (and `zn hooks install --project` in each project that uses a project hook) so the written hooks get the fixed guard.
- Windows: the hook commands now name `powershell.exe` by its full path (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` in the Codex project hook, which `cmd.exe` runs). Before, `cmd.exe` looked in the current folder first, so a `powershell.exe` placed in the project could run in its place; in 1.13.1 the Codex project hook (`zn hooks install codex --project`) ran `zn hook codex` the same way. On Windows, run `zn hooks install <agent>` again for each agent you set up (Codex, Cursor, Gemini CLI, GitHub Copilot CLI, Antigravity, ZCode) and `zn hooks install codex --project` in each project that uses it; `zn-gate check` now reports a hook that still starts `powershell.exe` by name.
- OpenCode project plugin: `zn` and the Node.js it starts are looked up only in the absolute PATH entries, and a hook that ends without reading its input no longer crashes OpenCode.
- Programs zn-gate starts by name now come from the absolute PATH entries only, never from the current folder or a relative PATH entry: `git` (checked when a file write holds secret placeholders), the MCP server command under `zn-gate shield` (which now also starts the server with that PATH and, on Windows, without the current-folder search, so `cmd /c npx ...` or `sh -c ...` cannot pick a program from the project), the `claude` CLI during `zn hooks install`, and `sh` in `zn-gate check` and the Antigravity self-check. zn-gate also runs `git` with `core.fsmonitor` turned off, so a program named in the repository's `.git/config` does not run, and treats a repository git refuses to read as possibly committed. In 1.13.1, a `git.exe` or a server program of the same name placed in the project could run instead on Windows, or anywhere through a relative PATH entry.
