### Security
- Python: `echo <Base64 without = padding> | base64 -d` is now decoded and checked like padded Base64, as in Node.js. Before, unpadded Base64 that hid a blocked command was allowed.
- Python: `check_tool_call`, `check_tool_result`, `@guard` and `guarded_tool` now read the strings inside dataclasses, pydantic models, other objects (through their attributes), dict views and file-system paths, as Node.js does with objects. Before, a blocked string inside any of them was allowed. A generator or other one-shot iterator is now blocked (rule `type:unscannable`), because checking it would use it up: pass a list instead. The `self` or `cls` of a guarded method is not checked.
- Python: `sanitize_tool_result(tool_name, content)` with a dict, list or object now checks each real string value and the JSON text, as Node.js does, and `sanitized_content` is that JSON text. Before, the text was built with `str()`, which hides BiDi and zero-width characters, so such output was marked safe.
- Python: `@guard(on_block="custom")` now raises `GuardBlockError` after the callback returns, so a blocked call never runs the function and a blocked result is never returned. `on_block="custom"` without a `callback` raises `ValueError` when the decorator is created.
- Python: `check_tool_call` and `@guard` now check argument strings longer than 256 KB in overlapping windows up to 4 MB, as tool results are, instead of only their start and end. Past 4 MB the result has `truncated=True`, and `block_truncated=True` (new in `check_tool_call`; in `@guard` it now covers arguments too) or `ZN_BLOCK_TRUNCATED=1` blocks it.
